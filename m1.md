# M1 plan: the first intent-conditioned inspection pipeline

**M1 should deliver a working, TypeScript-first inspection pipeline—not just new models around the existing orchestration.** Resolution, collection, policy, scoring, selection, and rendering should become independently replaceable, with a debug trace showing how a request passed through them.

I recommend making all five intents first-class policy profiles in M1, while being explicit about their initial limitations. `rename`, for example, should collect rename-relevant evidence; it should not claim that a rename is safe or produce edits.

## 2. Define M1’s outcome precisely

The M1 acceptance statement should be:

> Given a target and intent, `agentq inspect` resolves the target conservatively, determines available capabilities, acquires bounded observations, applies an explicit evidence policy, scores and selects evidence using inspectable heuristics, and returns a bounded bundle with provenance and gaps.

The architecture must establish these invariants:

**Changing scoring does not change resolution or collection.** For the same request, collection policy, repository state, and providers, changing relevance weights must operate on the same evidence pool.

**Changing selection does not change observations.** A selector chooses from acquired evidence; it does not perform hidden searches.

**Changing a provider does not require changing orchestration.** Adapters normalize their results into inspection contracts.

**Rendering does not make evidence decisions.** It serializes the selected bundle; it does not independently truncate away required evidence.

**Debugging does not change behavior.** Enabling debug must not change provider requests, selected evidence, request identity, or normal output.

### M1 scope

M1 should include all five intent profiles, typed targets, TypeScript capabilities, a compatibility adapter for existing Python functionality, generic repository capabilities, an internal budget policy, a deterministic baseline scorer and selector, and structured debugging.

M1 should **not** include persistent replay, `expand`, or `refresh`. Those remain M2 work. This narrows the earlier roadmap deliberately: we should first make one inspection reliable and independently testable before introducing persistent inspection lifecycles.

`search` and the existing search-oriented `continue` remain available during this transition.

## 3. Directory structure and dependency direction

Use the proposed `inspection/` package, with a few explicit additions for capabilities, budgeting, and debugging.

```text
agentq/src/agentq/
├── inspection/
│   ├── __init__.py
│   ├── contracts.py       # Typed requests, observations, plans, results
│   ├── service.py         # Pipeline orchestration
│   ├── resolution.py      # Candidate identity and resolution decisions
│   ├── capabilities.py    # Capability vocabulary, registry, availability
│   ├── acquisition.py     # Collection planning and bounded execution
│   ├── policy.py          # Intent requirements and policy assessment
│   ├── features.py        # Pure feature extraction
│   ├── scoring.py         # Named, versioned relevance heuristics
│   ├── selection.py       # Required evidence, diversity, budget selection
│   ├── budgeting.py       # Internal acquisition and delivery limits
│   ├── rendering.py       # Canonical bundle projection and serialization
│   ├── lifecycle.py       # M1: source-version and candidate validation only
│   ├── debug.py           # Trace models and collection; no stream writes
│   └── adapters/
│       ├── __init__.py    # Default adapter composition
│       ├── typescript.py
│       ├── python.py
│       └── repository.py # Read, outline, lexical search, ownership
│
├── navigation/
│   ├── models.py         # Provider-specific models retained as needed
│   └── providers/        # Existing low-level navigation implementations
│
├── discovery/            # Existing search/read/outline primitives
├── workspace/            # Existing ownership and graph primitives
├── delivery/             # Transport, receipts, and delivery bookkeeping
├── continuations/        # Existing search continuation support
└── cli/                  # Argument parsing and stream handling
```

This is a responsibility map, not an instruction to create an interface class for every module. Most stages should be ordinary functions operating on immutable records.

### Dependency rules

```text
CLI / integration adapter
          ↓
inspection service
          ↓
resolution / policy / acquisition / scoring / selection
          ↓
inspection contracts and capability interfaces
          ↑
concrete inspection adapters
          ↓
existing navigation / discovery / workspace primitives
```

`service.py` must not import `TypeScriptProvider`, inspect provider payload classes, or branch on language names.

The default registry should be assembled at the composition boundary and passed into the service. Do not replace the existing hard-coded provider tuple with a larger hard-coded tuple hidden inside orchestration.

Keep `core/languages.py` as a catalog of language and ecosystem facts. It already explicitly separates those facts from semantic behavior; the capability registry should not be added to that foundational module.

## 4. The pipeline and its intermediate products

Use explicit intermediate results rather than a mutable “inspection context” containing everything.

| Stage                 | Responsibility                                                 | Product             |
| --------------------- | -------------------------------------------------------------- | ------------------- |
| Normalize             | Validate target syntax, scopes, coordinates, and intent        | `InspectionRequest` |
| Discover capabilities | Determine applicable adapters and runtime availability         | `CapabilityReport`  |
| Resolve               | Acquire candidates, validate identities, expose ambiguity      | `ResolutionResult`  |
| Compile policy        | Determine evidence requirements for the intent and target kind | `EvidencePolicy`    |
| Plan collection       | Match policy requests to capabilities and internal limits      | `CollectionPlan`    |
| Acquire               | Execute the plan and normalize observations                    | `EvidencePool`      |
| Extract and score     | Calculate observable features and relevance contributions      | `ScoredEvidence`    |
| Select                | Choose evidence and representations under constraints          | `SelectionPlan`     |
| Assess and render     | Assess what was actually selected and serialize the bundle     | `InspectionBundle`  |

Ambiguous or unresolved requests should finish with a valid resolution response. They should not continue collecting evidence as though an arbitrary candidate had been selected.

A simplified orchestration should read approximately like this:

```python
capabilities = registry.describe(request, context)
resolution = resolve(request, capabilities, context)

if not resolution.has_selected_target:
    return build_resolution_bundle(request, resolution, capabilities)

policy = compile_policy(request, resolution)
collection_plan = plan_collection(policy, resolution, capabilities, limits)
pool = acquire(collection_plan, registry, context)

features = extract_features(request, resolution, pool)
scores = score_evidence(features, scoring_profile)
selection = select_evidence(pool, scores, policy, delivery_budget)

assessment = assess_selected_evidence(policy, pool, selection)
return build_bundle(request, resolution, selection, assessment)
```

The actual implementation should make each stage observable through the trace collector, but should remain this direct.

### Important separation: collection policy versus ranking policy

The intent can change what gets collected. For example, `edit` may request test evidence that `understand` does not prioritize.

However, **changing a weight in `scoring.py` must not change `CollectionPlan`**. Otherwise an experiment nominally comparing scoring is also comparing different retrieval behavior.

## 5. Concrete typed models

The current navigation models already use dataclasses and runtime validation, and the project targets Python 3.10+. Continue that approach rather than adding a modeling dependency. Use `Enum` plus `str`, not `StrEnum`, and reuse the existing validation helpers.

### 5.1 Requests and targets

Separate the semantic request from execution and presentation settings:

```text
InspectionRequest
  intent
  target

InspectionContext
  repository root and identity
  request identity
  internal limits
  capability registry / execution dependencies

PresentationOptions
  output format
  debug enabled
```

There must be no agent-provided budget in `InspectionRequest`.

Recommended target contracts:

| Target            | Required information                      | M1 behavior                                                                                  |
| ----------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `SymbolTarget`    | Name; optional declaration scopes         | Search for declaration candidates; never reinterpret a lexical hit as a resolved declaration |
| `PathTarget`      | Repository-relative file or directory     | Inspect structure and ownership; no implicit selection of a symbol                           |
| `LocationTarget`  | Path, line, column                        | Resolve the entity at that position when supported; otherwise report the limitation          |
| `RangeTarget`     | Path and explicit source ranges           | Return exact bounded source evidence with range-specific policy                              |
| `CandidateTarget` | Candidate ID and original symbol selector | Reacquire candidates and validate the selected ID before use                                 |

**For M1, candidate IDs should remain request-bound selectors, not standalone durable handles.** The original symbol and declaration scopes are available in the existing CLI flow, so there is no need to build a persistent candidate database yet.

Preserve existing multiple source anchors/ranges within one file. General cross-file multi-target orchestration can wait until M2.

#### Coordinate and scope rules

Define one canonical coordinate convention: one-based lines and columns, with columns measured in Unicode code points and end positions exclusive. Adapters must convert their native offsets.

A line-only source anchor is not the same as a semantic cursor position. `--line 40` can retain source-preview semantics; `--line 40 --column 8` can express a `LocationTarget`.

Keep **declaration scope separate from evidence scope**. Narrowing candidate resolution to `src/orders/service.ts` must not silently restrict reference acquisition to that file.

### 5.2 Resolution

Prefer a discriminated result over one dataclass with many optional fields:

```text
ResolvedTarget
  selected target
  selection method: exact_location | unique_candidate | explicit_candidate
  candidate acquisition coverage

AmbiguousTarget
  candidates
  total/count quality
  candidate acquisition coverage

UnresolvedTarget
  reason: not_found | incomplete | unavailable | failed | stale_candidate
  diagnostics
  candidate acquisition coverage
```

Do not introduce a numeric “confidence” field in M1. The existing conservative candidate-selection rule is a better baseline than an uncalibrated score.

### 5.3 Evidence and decisions

| Model                 | Principal fields                                                                              |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `Observation`         | ID, kind, typed payload, source references, source versions, acquisition reference            |
| `AcquisitionRecord`   | Capability, provider/version, method, effective scope, coverage, diagnostics, observed inputs |
| `EvidenceVariant`     | Observation ID, representation kind, source span, fidelity, renderable content                |
| `EvidencePool`        | Observations, acquisition records, relationships, collection limitations                      |
| `EvidenceRequirement` | Requirement ID, acceptable evidence, strength, satisfaction rule                              |
| `EvidenceFeatures`    | Observable relation, role, binding information, source characteristics                        |
| `ScoreBreakdown`      | Total and named contributions, scoring profile version                                        |
| `SelectionPlan`       | Selected variants, required-evidence decisions, omissions, measured cost                      |
| `PolicyAssessment`    | Per-requirement status and supporting observation IDs                                         |
| `InspectionBundle`    | Schema version, request, resolution, selected evidence, assessments, gaps                     |
| `InspectionTrace`     | Stage events, counts, timings, decisions, profile versions                                    |

Reuse `Coverage`, `Diagnostic`, `SourceRef`, and provider-result vocabulary where appropriate. Do not introduce competing coverage definitions.

The existing `EvidenceRecord` represents presented evidence and has a mapping payload. Keep it as a delivery boundary where useful; do not make an unrestricted `dict[str, Any]` the internal observation model.

### Observation versus representation

This distinction must exist in M1:

```text
Observation:
  declaration of listOrders at a versioned source location

Representations:
  signature
  exact declaration body
  bounded excerpt
```

A bounded excerpt must not satisfy a requirement for an exact declaration body. A signature and body from the same declaration must not be treated as two independent discoveries.

## 6. Capability registry and adapters

### 6.1 Capabilities describe operations, not languages

Use capability identifiers such as:

```text
find_declarations
resolve_location
read_source
outline
semantic_references
syntactic_mentions
lexical_mentions
implementations
owning_package
```

“Related tests” is initially a collection recipe rather than a language primitive: acquire semantic references in test files where available, and separately acquire lexical test mentions.

Do not use capability names such as `complete_references` or `safe_rename`. Completeness is a property of a particular acquisition within a declared scope, not a permanent capability.

### 6.2 Initial capability coverage

The following is the proposed M1 registration:

| Capability             | TypeScript/JavaScript adapter           | Python adapter                                      | Repository adapter                             |
| ---------------------- | --------------------------------------- | --------------------------------------------------- | ---------------------------------------------- |
| Declaration candidates | Language-service navigation             | Existing AST definitions                            | No generic declaration guarantee               |
| Location resolution    | Language-service definition lookup      | Unsupported initially unless implemented explicitly | Exact source read only                         |
| Source content         | Delegate to repository adapter          | Delegate to repository adapter                      | Supported                                      |
| Outline                | Reuse existing outline mechanisms       | Reuse existing outline mechanisms                   | Availability depends on installed tools/parser |
| Semantic references    | Supported within loaded project context | Unsupported                                         |                                                |
| Syntactic mentions     | Not needed for initial TS path          | Existing AST-name evidence                          | Unsupported                                    |
| Lexical mentions       | Delegate                                | Delegate                                            | Existing search                                |
| Implementations        | Existing language-service operation     | Unsupported                                         | Unsupported                                    |
| Owning package         | Delegate with ecosystem information     | Delegate with ecosystem information                 | Existing ownership lookup                      |

The TypeScript bridge already calls definition, reference, and implementation APIs. Python currently provides syntax-aware definitions and explicitly non-semantic reference evidence. Those are the capabilities to adapt—not hypothetical richer providers.

### 6.3 Separate support, availability, and outcome

These are different facts:

```text
Unsupported:
  No adapter implements semantic references for this language.

Unavailable:
  The TypeScript adapter implements references, but its runtime or project
  configuration is unavailable.

Empty:
  The reference query completed within its stated scope and returned zero results.

Partial:
  Some evidence was returned, but collection was limited or a subquery failed.
```

A missing capability must not force every adapter to implement a dummy method. Use a small registry of capability handlers and narrow resolution/collection interfaces.

Availability should be checked against the same runtime and project configuration that acquisition will use. Checking only for `node` is insufficient.

### 6.4 Required TypeScript bridge changes

M1 needs a limited bridge refactor, not a language-server rewrite.

**Expose acquisition metadata.** Return the TypeScript version, configuration identity, effective project scope, and truncation/failure reasons.

**Make discovery limits visible.** The current bridge limits configuration/directory discovery and bounds `getNavigateToItems()` before exact-name filtering. Those limits must be reflected in candidate coverage. The current swallowed navigation exception must become a diagnostic.

**Use exact selected locations.** After resolution, query the validated declaration location rather than reselecting through a display index.

**Allow a bounded batch of requested operations.** One adapter invocation should be able to request the required definition/reference/implementation sections without creating a separate Node process for every logical capability.

**Keep completeness scoped.** A TypeScript language-service instance corresponds to a project context; repository-wide completeness cannot be inferred merely because one service returned an untruncated list. The official API documentation makes that project boundary explicit. ([GitHub][1])

Multi-project reference acquisition can improve in M2. M1 must report its limits accurately.

## 7. Intent policies and readable scoring

### 7.1 All five intents should have actual policies

Do not add enum values that all dispatch to the old `edit` implementation.

| Intent       | Initial collection emphasis                                                                    | Explicit limitation                                                                        |
| ------------ | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `understand` | Target description/source, definitions, representative references, implementations, ownership  | Representative context, not exhaustive dependency analysis                                 |
| `edit`       | Exact requested source, relevant references, test evidence, ownership/configuration            | Does not authorize an edit or establish behavioral correctness                             |
| `rename`     | Declaration identity, semantic references, separately labeled lexical mentions, relevant tests | No proposed-name collision analysis or complete rename guarantee                           |
| `refactor`   | Requested source, implementations, consumers, tests, ownership                                 | No proof of behavior preservation or automatic invariant discovery                         |
| `impact`     | Direct references/implementations, test evidence, package ownership                            | Potential impact around the target, not diff-conditioned or transitive impact completeness |

For file and directory targets, compile target-appropriate policies. A directory inspection should not pretend that returning an outline satisfies “all editable source acquired.”

### 7.2 Requirements precede scores

Requirements need distinct satisfaction rules.

For example:

```text
Requirement: selected_source
Rule: an exact source representation of the requested span must be selected.

Requirement: test_search
Rule: the requested test-domain acquisition must have an explicit outcome.

Requirement: representative_reference
Rule: select an admissible reference when one was acquired.
```

An empty, completed test search can satisfy “search attempted and reported.” It does not establish that no relevant tests exist anywhere.

Policy assessment must happen against **selected evidence**, not just the acquired pool. Acquiring an exact body and then omitting it from the bundle must leave the source requirement unsatisfied.

### 7.3 Initial scoring heuristic

Start with a small, named, versioned linear heuristic. Do not begin with learned ranking, embeddings, or a large collection of interacting bonuses.

An initial optional-evidence priority table could be:

| Evidence role              | Understand | Edit | Rename | Refactor | Impact |
| -------------------------- | ---------: | ---: | -----: | -------: | -----: |
| Reference/use site         |          6 |    6 |      8 |        6 |      8 |
| Implementation             |          6 |    4 |      2 |        8 |      6 |
| Test evidence              |          2 |    8 |      4 |        8 |      6 |
| Ownership/configuration    |          4 |    6 |      4 |        6 |      6 |
| Additional lexical mention |          2 |    2 |      4 |        2 |      4 |

**These are proposed baseline priorities, not empirically established coefficients.** Required source evidence is handled separately and is not competing in this table.

A deliberately small scoring rule:

$$
\operatorname{score}(e)
=
\operatorname{role\_priority}(e,\text{intent})
+
\operatorname{binding\_bonus}(e)
$$

For example, a binding-resolved reference can receive a named bonus of two; a lexical mention cannot. Apply that bonus only to relevant relationship-bearing evidence, not indiscriminately to everything produced by TypeScript.

A debug explanation should look like:

```text
observation: obs-17
score: 10
contributions:
  test_evidence_priority: 8
  binding_resolved: 2
```

Keep these rules in `scoring.py`, with the observable inputs in `features.py`.

Do not put provider names, token costs, or “already selected similar evidence” into this score. Provider identity is not relevance; cost and redundancy belong to selection.

### 7.4 Initial selector

Use a deterministic constrained selector:

1. Reserve the response envelope and required evidence.
2. Prefer representation of important requested evidence roles before repeatedly selecting the same role.
3. Fill remaining capacity using relevance per incremental rendered cost, accounting for duplicate and overlapping evidence.
4. Reassess requirements and serialize the exact final bundle.

Use stable source-location/observation-ID tie-breakers.

Keep diversity simple initially: avoid spending the response on many overlapping excerpts or repeated use sites from the same file while other useful roles remain unrepresented. Record the selection reason separately from the relevance score.

Do not claim an optimality guarantee for this heuristic.

## 8. Internal budgeting and delivery

**I agree that the coding agent should not set the budget.**

Remove `--budget` from the public parsers and integration contract. Remove the hidden `--scan-cap` as well; test-specific limit injection belongs in internal test dependencies, not hidden production arguments.

### Internal limits

Separate two internal configurations:

```text
AcquisitionLimits
  candidate and observation limits
  file/source limits
  provider-call limits
  execution deadline

DeliveryBudget
  maximum serialized output characters
  response-envelope allowance
```

For M1, retaining the current **12,000-character delivery ceiling** is a reasonable baseline. That preserves a known starting point while relocating ownership into `agentq`; it is not a claim that 12,000 is optimal. The current common parser uses that default.

Similarly, initially retain useful existing collection defaults—such as bounded reference collection and twelve lexical test mentions—but give them named internal fields and explicit omission reporting. Avoid simultaneously changing architecture and extensively retuning collection.

### Cost accounting

Selection must account for the actual requested output format, including JSON escaping, separators, provenance, gaps, and the terminal newline.

Do not use character counts as an unlabeled token estimate.

Do not preserve the current “half for declaration, one third for navigation” renderer allocation. The policy and selector should determine the evidence mix.

When required evidence cannot fit, return a partial assessment with the missing requirement. Do not silently shorten exact source and retain an “exact” label.

### Delivery integration

The current `emit_cached()` performs suppression, attaches continuations, and invokes generic output projection. The new inspection path must not pass a selected bundle through a second evidence-dropping projection.

Add a preselected/pre-rendered delivery path that preserves existing write-then-receipt behavior.

For M1, **bypass inspection-level repeat suppression and source suppression during collection**. Otherwise a previously delivered snippet can disappear from a new policy-required bundle. Keep delivery receipts, but defer evidence reuse and consumer-context lifecycle semantics to M2.

Do not globally remove search caching or rewrite unrelated delivery behavior.

## 9. Debugging and minimum source validation

### `--debug`

Add:

```bash
agentq inspect listOrders --intent edit --debug
```

Normal text or JSON remains on stdout. Structured debug events go to stderr.

The trace should include:

| Stage              | Useful metadata                                           |
| ------------------ | --------------------------------------------------------- |
| Normalization      | Target kind, intent, validation outcome                   |
| Capabilities       | Applicable handlers, unavailable capabilities and reasons |
| Resolution         | Candidate counts, coverage, selection method              |
| Policy             | Profile version, requirement IDs                          |
| Collection         | Requested capability, counts, duration, caps, failures    |
| Scoring            | Feature values and named contributions                    |
| Selection          | Selected IDs, omission reasons, diversity decisions, cost |
| Assessment         | Satisfied and unsatisfied requirements                    |
| Rendering/delivery | Final size, consistency checks, delivery outcome          |

Example:

```json
{
  "stage": "selection",
  "status": "completed",
  "profile": "selection-v1",
  "acquired": 31,
  "selected": 9,
  "omitted": {
    "redundant": 8,
    "delivery_budget": 14
  },
  "required_missing": [],
  "output_chars": 10842
}
```

Trace recording belongs in `inspection/debug.py`; writing to stderr belongs in the CLI. That preserves the existing architectural rule that capability modules do not write directly to stdout or stderr.

Bound trace size and report dropped events. Do not include source bodies, raw queries, arbitrary provider payloads, absolute paths, or unfiltered exception text in debug records.

Add `debug` to presentation-only argument handling so it cannot alter semantic request identity. The current emitter explicitly maintains that distinction.

### `lifecycle.py` in M1

This module should do real but limited work:

* Validate candidate source versions before accepting a candidate.
* Associate observations with source/configuration versions.
* Detect known input changes during an inspection and mark affected results unstable.

Do not label the result an atomic repository snapshot. M1 can provide versioned observations and best-effort consistency checks without implementing full repository snapshotting.

Persistent invalidation, new-file detection for prior negative searches, and cross-request refresh belong in M2.

## 11. Test plan

Favor small decision fixtures and boundary tests. Do not create another large integration suite that mocks provider internals to test scoring.

### New focused tests

| Test area             | Essential cases                                                                                                                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request contracts     | Invalid intent, invalid coordinates/ranges, path confinement, explicit path missing, candidate missing original selector                          |
| Resolution            | Unique complete candidate; duplicate names; truncated candidate acquisition; applicable provider unavailable; stale candidate; explicit selection |
| Capability registry   | Missing capability, unavailable runtime, inapplicable adapter, empty successful result, fake third-language adapter                               |
| TypeScript adapter    | Definition/reference/implementation normalization; exact-location selection; discovery cap; navigation failure; configuration scope               |
| Coordinate conversion | Non-ASCII and astral characters before a target; correct Python byte-offset and TypeScript offset conversion                                      |
| Policy                | Each intent requests appropriate evidence; path/range policies differ; completed-empty test search is not “no tests exist”                        |
| Features/scoring      | Named contribution arithmetic; unknown features remain unknown; provider name does not determine score                                            |
| Selection             | Required source survives; exact body versus excerpt; overlaps; diverse roles; deterministic ties; insufficient budget                             |
| Coverage              | Acquisition truncation versus selection omission; missing capability cannot become a complete empty result                                        |
| Debug                 | Stdout and decisions unchanged; trace bounded; failures recorded; sensitive text excluded                                                         |
| Delivery              | Valid bounded JSON; no secondary truncation; receipt describes emitted evidence; failed writes do not record delivery                             |
| Architecture          | Pure stages cannot import execution, filesystem acquisition, CLI, or concrete adapters                                                            |

### The three most important isolation tests

**Scorer replacement:** collect once, run two scoring profiles, and assert identical resolution, collection plan, provider-call history, and evidence pool.

**Selector replacement:** run two selectors against the same scored pool and assert no additional provider calls.

**Adapter replacement:** register a fake language adapter and complete an inspection without modifying `service.py`, `policy.py`, `scoring.py`, or `selection.py`.

These are the direct tests of your M1 objective.

## 12. Implementation sequence and M2 boundary

### Suggested M1 implementation slices

| Slice                                   | Deliverable                                                                | Exit criterion                                                                                      |
| --------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| **M1.1 — Contracts and boundaries**     | New package, typed targets/results, architecture rules, fake adapter       | A fake inspection can traverse the stages without CLI or provider-specific dependencies             |
| **M1.2 — Capabilities and resolution**  | Registry, TypeScript adapter, Python adapter, conservative resolution      | Unique, ambiguous, unavailable, partial, and stale-candidate outcomes are correct                   |
| **M1.3 — Collection and policies**      | Repository adapter, evidence pool, five intent profiles                    | Intents produce explicit collection plans and truthful capability gaps                              |
| **M1.4 — Scoring and selection**        | Features, score breakdowns, internal budget, selector                      | Scorer/selector isolation tests pass; selected evidence satisfies or explicitly misses requirements |
| **M1.5 — CLI and delivery migration**   | New `inspect`, debug, integration update, removal of old orchestration     | No public tuning flags, no stale recovery commands, no secondary evidence truncation                |
| **M1.6 — Validation and documentation** | Real TypeScript fixtures, migrated regressions, architecture documentation | Tests/static checks pass, including non-skipped TypeScript execution                                |

Implement `understand` end to end first, then `edit`, then the remaining policy profiles. All five should be real by M1 completion, but they need not be developed simultaneously.

### M2 and later work

| Area                | M1                                                      | M2                                                                     |
| ------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| Evidence pools      | Explicit, in-memory, independently testable             | Persisted replay records and offline comparisons                       |
| Scoring             | Named deterministic baseline                            | Labeled fixtures, ablations, relevance/diversity experiments           |
| Follow-ups          | Candidate reselection and supported search continuation | `expand` with typed evidence handles                                   |

| Candidate identity  | Request-bound reacquisition                             | Durable handles with explicit expiry and snapshot semantics            |
| Targets             | One logical target; existing same-file ranges           | General multi-target requests and change/diff targets                  |
| TypeScript scope    | Truthful loaded-project scope                           | Broader project-reference and cross-project acquisition                |
| Specialized intents | Evidence-oriented initial profiles                      | Rename conflicts, richer refactor contracts, change-conditioned impact |

Learned ranking, embeddings, LLM reranking, background provider daemons, dynamic plugin loading, automated edits, and proving cheaper-model/frontier-model parity are **not M1 requirements**. Some may follow M2 experiments; they should not all be prerequisites for M2 either.

## M1 sign-off standard

M1 is complete when a reviewer can answer these questions directly from the code and debug output:

> Why was this target selected?
> Which capabilities were available?
> What evidence was requested and acquired?
> Why did each selected item receive its score?
> Why was another item omitted?
> Which requirements remain unsatisfied?
> Can the scorer, selector, or adapter change without disturbing unrelated stages?

**That is the foundation to optimize for: a working pipeline whose decisions are explicit and whose components can be changed in isolation—not an early claim that its evidence ranking is already optimal.**
